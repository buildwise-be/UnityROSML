# Known Issues

- Contact-target and execution-frame fixes are local source changes until
  deployed by an authorized operator. Pick/place yaw uses twelve 30-degree
  alternatives, and legacy vacuum result/execution messages still have no
  request IDs. Depth offsets are positional contact commands, not force control
  or proof of actual foam compression. Synthetic preview ownership is tracked
  only within one task-node process; unknown/manual/attached/executed scene
  objects are intentionally preserved. Hardware behavior remains unverified.

- Exact TCP A/B source and offline package validation are complete, but ROS-TCP transport, physical planning/alignment and execution remain unverified; no deployment or real-stack application launch was performed. The later network-isolated mock-scene smoke produced contact and exact-TCP preview plans. One existing scene-effect test fails at `test_scene_effects.cpp:166` because the expected tile/hand ACM entry is absent. The same assertion fails on the untouched baseline in the current MoveIt image. The new TCP path has request matching and no IO, but adds no cancellation or shared execution ownership; external clients can still move the robot or change the scene.

- `kenos_sl` is registered in startup choices, driver routing, SRDF and MTC definitions. Its changer/adapter cylinder still uses the owner's approximate axial reach and unmeasured radius/clocking; physical adapter centring, working foam compression and payload require installation-specific verification. The owner confirmed the same DO3 vacuum settings as Kenos; wiring and physical IO behavior have not been exercised. Source/model checks do not validate a mounted tool or runtime planning; full ROS build/launch/model tests remain unrun locally.
- The owner raised inconsistent tool integration; static review confirmed separate model inputs and hardcoded task behavior. Evidence and proposed corrections are in the [architecture review](ARCHITECTURE_REVIEW.md).
- First P1 corrected in the working tree on 2026-09-09: primary bringup/control/MoveGroup/MTC launches now explicitly share tool, UR type and arm-calibration inputs. Six source-derived Xacro scenarios passed. The seven registered model-consistency cases passed in the 2026-10-21 application-image verification; see [verification details](../wiki/BUILD_AND_TESTING.md).
- Second P1 corrected in the working tree on 2026-09-10: custom execution now applies scene effects after each successful step and requires acknowledgement before advancing. Validation and its limits are recorded in [build/testing](../wiki/BUILD_AND_TESTING.md).
- Third P1 corrected in the working tree on 2026-09-10: execution requires a successful immutable plan that has not already been consumed. New planning/scene setup invalidates readiness; initialization/planning failures do not fall through. Start joints and collision-scene assumptions are checked before operation. The portable admission tests passed; ROS-dependent validation tests remain unrun. Full node compilation subsequently passed in the October 21 WSL application build.
- Fourth P1 corrected in the working tree on 2026-09-14: explicit TCP topics preserve frame/time meaning and reject malformed commands; a startup opt-in retains legacy wrist input semantics. Indexed status reports planning/execution failures and stops later array moves. Eight portable tests passed; nine ROS-message/tf2 tests remain unrun. Commander compilation subsequently passed in the October 21 WSL application build.
- Fifth P1 corrected in the working tree on 2026-09-14: MTC's runtime tool selection matches launch model inputs, and a validated startup definition determines whether vacuum tasks are available. `none` rejects pick/place and execution before task scene updates or IO; basic TCP motion and explicit scene setup remain available. All five original P1 corrections are implemented; ROS/runtime validation remains outstanding.
- MTC startup now requires a matching `tool` parameter and URDF/SRDF plus the definition's `tcp` IK frame. Standalone vacuum-tool callers must specify `tool=kenos` or `tool=kenos_sl` to match their model; previous arbitrary `ik_frame` overrides fail configuration. Tool/TCP changes require restarting with a consistent model. Physical mounting, wiring and vacuum feedback are not verified by this software definition.
- Unity migration is required for the new TCP topics. Old topics are disabled by default and can be enabled explicitly for unmodified clients; do not merely rename a wrist-goal publisher to a TCP topic. The external client's coordinate conversions and compensated wrist offsets are unavailable for verification. See [API and migration](../wiki/API.md).
- Basic pose arrays use one frame snapshot at admission and plan/execute each target sequentially. Earlier moves are not rolled back on failure; a failed execution may have partially moved the arm. Status has no command identifier, and completed commands can be repeated by queued/duplicate inputs. Shared ownership with MTC, cancellation and end-to-end callback/TF/controller testing remain follow-up work.
- Execution recovery remains manual: failed/timed-out scene updates stop subsequent steps but do not roll back earlier motion, IO or scene changes. A timeout can still have changed the server scene; failure may leave partial effects. Vacuum is not automatically released. An execution attempt consumes the plan even if preflight or execution fails; inspect state before creating another plan.
- Preflight is a point-in-time check. Other clients can still move the arm or update the scene afterward. Exact collision-geometry comparison can conservatively reject equivalent representations. Recent joint feedback receipt is not proof of hardware acquisition freshness. The legacy Bool command has no plan ID: delayed messages can target a later plan, and callback-level busy rejection is not arrival-time deduplication. Model parameters are checked for changes, but a physically changed tool is not detected.
- Remaining model limitations: auxiliary RViz/setup-assistant launches use default builder discovery and stale SRDF metadata; RSP-specific safety and physical/visual/joint-limit overrides are not shared with planning. Choosing another UR type still requires supplying the appropriate calibration file; the default remains the stored UR16e calibration.
- UR control-macro compatibility correction implemented on 2026-10-21: the installed 3.9.0 driver requires `ur_type`, causing `Undefined parameters [ur_type]` with the previous wrapper. The control package now inspects the installed macro at CMake configure time and generates its wrapper with `ur_type` only when accepted; older signatures receive no extra attribute. Rebuild the control package after a driver update or overlay switch. The application image rebuilt all 58 packages; 23 generator/model-consistency tests and eight complete Xacro expansions passed with the exact 3.8.0 and installed 3.9.0 control macros, both tools, and both mock settings. Older-macro coverage used current other dependencies and does not establish full old-driver runtime compatibility. No ROS nodes or hardware were operated during these checks; hardware behavior and the Nordbo driver version remain unconfirmed. See [build details](../wiki/BUILD_AND_TESTING.md#ur-control-wrapper-generation).
- MTC Docker build blocker reported on 2026-10-21: `ros2-0.1.4` can load system pybind11 through `py_binding_tools` before adding its bundled copy, causing duplicate alias-target errors. The base image now applies the dependency-order backport from upstream commit `158908aba9156afb3cd58aa2a8afbb8f9ffc2f13`; see [build details](../wiki/BUILD_AND_TESTING.md#mtc-pybind11-dependency-ordering). Patch applicability/application, the full base build (48 packages), and the application build (58 packages) passed in WSL Ubuntu 24.04. MTC Python imports, application package discovery, and command-executable shared-library resolution also passed. ROS test suites, GUI, mock bringup, and hardware behavior remain unverified.
- Follow-up findings: anonymous commands/results, missing shared execution ownership and cancellation, startup readiness, dependency metadata and build reproducibility, and missing end-to-end task tests. An additive execution-status topic now reports readiness, rejection and completion.
- Runtime and hardware consequences remain unverified; model/syntax checks are not commissioning evidence.
